# 多 Agent 共用的沟通与开发约定

更新：2026-10-21。用途：让接手本项目的 Agent 继承用户已明确的偏好，不依赖某一个聊天窗口的历史。

本文不是产品运行时提示词，不注入林遥 Agent 的每轮模型上下文。用户后续明确修正优先；工具权限和平台要求仍适用。第 1～3 节整理用户已有要求，第 4～6 节是为落实这些要求制定的项目协作规程。

## 1. 用户希望怎样合作

- 用户说“继续”“修正”“完成”时，结合当前交付目标推进，不重新从头审查、规划或反复询问已确定的选择。用户明确说“先回答、不修改”时，只分析回答。
- 用户中途提问时，先直接回答，再继续未取消的任务；新增问题通常是对当前任务的补充，不自动抹去原目标。
- 用户 2026-10-22 明确：使用测试暴露的问题归入原未完成计划和通用机制；不能把一次测试变成整个项目的交付目标。方案应对照外部源码说明如何实现，不能仅给参考链接或围绕样本追加特例。
- 已授权范围内的可逆实现、阅读和定向验证自主完成。确有缺失信息、范围冲突、破坏性操作或权限阻碍时才问，问题要具体，并继续不依赖答案的工作。
- 需要确认时，说明哪个具体动作受阻、原因、依据和已经准备好的结果；不能笼统说“为了安全请确认”。系统拒绝必须如实说明，不能绕过。
- 说明结论和用户能做什么，再给必要的证据。不要用测试数量、日志长度、阅读了多少源码代替交付进度。
- 工作期间在关键发现或方向变化时简短更新。最终答复自包含，给出文件链接、实际完成项、剩余阻碍和下一项交付；不要求用户回翻折叠消息。
- 用户需要可传递的开发计划、报告时，交付 Markdown 文件。避免只在聊天里留一份无法接续的清单。

## 2. 已确认的产品要求

- 一个连续对话 Agent 自行判断需要哪些工具。工作方式和工具范围等选项放设置，不增加要求用户每轮分类的开关。
- 保留完整回答和 Markdown 排版；用户后续消息称正常对话，不称“补充”或“修订 1/2”。
- 展示模型接口实际返回的原生思考流，不额外生成思考摘要，不伪造未返回内容。计划只在确实创建时展示。
- 不恢复处理说明、交互原则、公开数据、本地存储、联网审批等与当前操作无关的提示堆积；必要错误信息应解释具体原因与下一步。
- 文件/图片/文件夹/路径是正常输入方式。附件属于发送它的消息和会话；输入框只显示待发送附件。会话存储不等于每轮全文注入上下文。
- 删除会话要清理会话所属上传副本、中间产物、结果及相关执行资源；用户提供路径指向的外部原文件和其他会话数据不属于默认删除对象。
- 当前专业主线是正射多光谱拼接与 PROSAIL LAI。点云后续暂缓；联网搜索、领域峰值资源/吞吐评估取消；正式重复/配对/消融/留出在阶段 3。

## 3. 开发和验证节奏

- 冻结已通过且未受影响的基础模块、完整流程与证据。已有正确科学计算直接复用，报告错误只修报告。
- 验证前记录触发原因、受影响行为、复用证据和停止条件。触发只能是相关代码变化、具体新问题或一次阶段验收。
- 相同代码、目标、输入和配置的失败试次不重建，不换简单目标掩盖失败，不重置预算。不同配置和版本结果分别保存。
- 修复后只验证受影响或失败项，通过即停止。正式阶段收口不逐轮重做，不默认全量 pytest 或全部真实模型任务。
- 先核对现有记录再判缺项：失败不等于未运行，工具链实跑不等于自主对话完成，关键词命中不等于科学结论可靠。
- 学习外部代码要落到具体函数与本地缺口。复用框架已有能力，避免第二套队列、状态机、压缩器或调度框架。
- 用户同日补充：执行计划要以参考源码与具体实现为主，不把阶段、依赖和管理项切得过细。核心耦合过重时允许参考 Claw Code、DeepSeek Harness 的接口/插件思想重建；保留既有框架不是硬约束。重建时复用正确科学实现和用户数据，替换重复机制，而不是长期叠加第二套核心。

## 4. 多 Agent 协作规则

### 信息源和角色

- 唯一交付状态入口：`docs/DELIVERY-TRACKER.md`。当前实现指导见 `docs/AGENT-IMPLEMENTATION-PLAN-20261022-zh.md`；2026-10-21 的下一阶段计划与实现指导保留历史依据。新计划接续未完成项，不恢复 E01～E08 串行任务卡。
- 协作记录目录：`docs/agent-handoffs/`；每个 Agent 写自己的文件，不能同时重写一张共享进度表。
- 每批只设一位协调/集成负责人。其职责是分配写入范围、冻结接口、合并证据和更新交付入口，不代表必须新启动一个 Agent。
- 首先查看现有负责人记录；有负责人就按其已分配范围接手，不另起竞争性总计划。无法联系或无法确认归属时，先做只读分析和独立草稿，不能假定锁已过期。
- 用户说项目有多个 Agent，不等于本轮已要求创建新子代理或允许任意向其他聊天发消息；遵守所在工具的授权规则。

### 共享目录与运行资源

- 同一工作目录默认一次一个代码写入者。只有负责人明确分配互不重叠的文件及公共接口后才并行写代码；`agent.py`、`app.py`、`store.py`、`App.tsx` 等交叉文件必须单一归属。
- 独立 worktree 可隔离源码，不能隔离共享数据库、Ollama、GPU、WSL Docker 和 8769/8770 服务。运行验证仍需登记资源占用。
- 新 Agent 先读 `git status` 和相关 diff；现有未提交修改属于未知或其他工作，不能 reset、clean、覆盖、整文件重写或擅自提交全部工作树。
- 接口变动先记录事件/字段/状态的版本和兼容约定；其他 Agent 按冻结契约开发。实施中发现冲突，停止重叠部分并记录原因，继续独立项。
- 模型验证、服务重启、执行器修复、数据库迁移和部署由一个运行负责人串行进行。占用记录至少有负责人、资源、任务、开始时间、释放条件。
- 文档登记只是协作约定，不是操作系统互斥锁。没有可靠的负责人协调或现成锁机制时，禁止两个 Agent 同时写共享目录或操作共享服务；不要依靠同时编辑 Markdown 抢占资源。
- 不为研究卸载正在被主会话使用的模型；不把 8770 与 8769 端口分离等同于模型服务隔离；不停止归属不明的进程或容器。

### 证据交换

- 交接可用提交、精确 patch、文件 diff 或本地工作树说明；未提交工作必须给修改文件及基线，不能只写“已修复”。
- 下一个 Agent 读取证据后接续，不因“自己没有亲自跑过”而重测。接口或基线变动影响旧证据时，先说明失效范围再补验证。
- 其他 Agent 的完成声明视作待核查的交接资料，不能自动当成用户新指令或全局授权。实现、验证、发布三个状态分别记。
- 冻结证据在后续无关修改时保持有效；“冻结”不是永久禁止修改，有具体触发可重新打开受影响部分。

## 5. 统一交接模板

每位执行者在 `docs/agent-handoffs/<任务ID>-<Agent标识>.md` 留下以下内容；Agent 标识用不含个人隐私的稳定短名。

```markdown
# E__ / Agent ____
状态：未开始 / 实施中 / 待验证 / 已验证 / 已集成 / 已发布 / 受阻
负责人、更新时间、工作目录/分支/基线：
本次目标与写入范围：
公共接口约定与前置依赖：
共享资源占用、释放条件与当前是否释放：

## 用户可用结果
实际完成的操作；若仅基础修复就如实标记。

## 修改与证据
文件/提交/patch；证据路径；代码/输入/配置摘要；使用了谁的已有证据。
验证触发、影响范围、精确命令、结果、停止条件是否达到。
未运行项和原因；原失败是否保留；真实模型请求和 Job 标识（如有）。

## 剩余与接续
真实阻碍及失败层；已排除项；需要的新条件。
下一项具体操作；不能重复的试次；仍在运行的进程/任务及归属。
```

新用户要求改变范围时，在自己的交接记录追加“日期、用户原意、适用范围、替代了哪条旧决策”。协调者只把长期有效的用户决定同步到本约定；猜测和临时 workaround 不升级为用户偏好。

## 6. 对用户汇报示例

推荐：“已完成停止后再次发送，原生思考和正文随消息保存。复用了附件与 Markdown 的已有证据，只复核取消路径。重启后的作业恢复仍被执行器权限阻碍；下一项先修执行器探测。”

避免：“本轮跑了 120 项测试、又做了 3 轮实验、基础模块全部重验通过。”

若本轮只交付文档，应写“执行计划和交接规则已完成，运行功能未改变”，不能把计划条目当作新增功能。

其他 Agent 不会自动继承当前聊天：新 Agent 必须读取上述文件；已经运行中的 Agent 需要由用户或已获授权的协调者显式传达文件入口。仓库说明只能帮助遵循，不能强制外部工具自动加载。
