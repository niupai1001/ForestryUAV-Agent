# 林遥 Agent 研发与自主能力研究（阶段A–D单遍筛查）

日期：2026-10-21。执行入口：`forestry-uav-agent-v1`。基线：**large + H2**，每项任务单遍，重复固定为 1。

本轮不开展正式重复、配对、消融或留出统计实验；结论只用于研发决策，不声称统计显著。点云后续、联网搜索、领域峰值资源/吞吐评估按用户 2026-10-21 的决定不再作为执行队列。

## 1 研究问题

1. **运行可靠性**：300 秒无输出、上下文提前耗尽，分别发生在模型服务、请求协议、上下文构建还是界面传输？
2. **自主执行能力**：Agent 能否根据自然语言目标选择工具、读取证据、修复错误并完成交付？
3. **科学判断能力**：Agent 能否复用既有多光谱成果，正确解释结果、识别适用性问题，并区分证据、假设和未知？

### 3.5 任务 04/05/07 整批失败于 `attempt to write a readonly database`

现象：凡是要真正执行代码的任务，run 都在模型返回工具调用之后立刻 `paused`，blocker 只有一句 `MODEL_PROTOCOL_ERROR: attempt to write a readonly database`，没有调用栈。最初怀疑是磁盘权限、WAL/journal 或我自己的只读连接，逐项排除后发现都不成立：

| 检查 | 结果 |
|---|---|
| `state.sqlite` / `model-steps.sqlite` 文件属性与 ACL | 可写（`YZH:(F)`，`attribute A`），非只读 |
| 用同样参数直接对 `model-steps.sqlite` 建表 + 插入 | 成功；`PRAGMA journal_mode` 返回 `wal` |
| 单独调用 `SqliteStepStore.record_tool_effect` | 成功 |
| 失败瞬间的同点探针（同一进程、同一秒） | 两个库 `write=ok` |
| 4 线程并发 `record_tool_effect` | **3/4 线程失败**：`OperationalError: attempt to write a readonly database` |

根因：`SqliteStepStore(database=...)` 每次调用都新开一条连接，并在每条连接上执行 `PRAGMA journal_mode=WAL`；该库文档自述只保证“并发读 + 单写”。本应用会在一个回合内**并行**发起多个工具调用（任务07 第 2 个请求同时调 `read_file` + `list_files`），于是多条连接并发写同一文件，一方关闭连接时删掉 `-wal`，另一方随即退化为只读。单动作任务（任务01/02/06）从未触发，所以此前一直被误读成模型问题。

修复：改用该库支持的调用方单连接（`check_same_thread=False`，`isolation_level=None`，`threadsafety=3` 串行化），连接建立时把 journal 模式与 `busy_timeout` 设一次，并先单线程建表（含 media 表），避免多线程同时 `executescript`。
复核：任务07 从“2 个请求后即暂停”变成 6 个请求、6 个动作、424 秒真实执行，`code.execute` 首次真正落到容器。

### 3.7 输入授权缺陷

任务07 第 4 个请求返回 `PRECONDITION_MISSING`：通用代码作业只接受无链接的单文件输入，目录授权只用于浏览。契约里 04/07 原来给的是目录，等于把“能否执行”变成了不可满足项。已改为逐文件授权（`height_summary.py` + `plots.csv`、`plot_stats.py` + `data/plots.csv`）。这属于契约缺陷修正，不放松验收条件：数值与产物判据未改。

### 3.8 作业执行器：本轮环境的硬限制

任务07 在只读库修好之后暴露下一层：`code.execute` 被接受并排入 Job，但执行器起不来。

| 观察 | 证据 |
|---|---|
| 作业停在 `queued`，模型侧看到 `EXECUTOR_UNAVAILABLE (WinError 5 拒绝访问)` | 任务07 第二轮，6 请求 / 6 动作 / 900 s 撞墙钟 |
| `wsl.exe` 被研究环境的程序黑名单拦截 | `PROGRAM BLOCKED BY SECURITY POLICY … 该拦截不可批准、不可绕过` |
| 本机 Docker 可用（服务端 29.1.3），只读挂载正常 | `docker run -v <workspace>:/x:ro` 成功列出目录并执行 Python |

产品本身支持两条执行路径（`jobs.py` 里 `docker_distribution` 为空即走本机 Docker）。研究实例试过改用本机 Docker，结果**准入层直接拒绝**：

> `PRECONDITION_MISSING`：当前资源准入支持实测 WSL 后端，Docker Desktop 虚机资源尚无已验证探测器。

这条拒绝是产品的正确行为（未验证后端不得放行），不能绕过，也不该绕过。因此在本环境里，容器作业有两条结局、都不可用：

| 执行路径 | 模型侧看到 | 代价 |
|---|---|---|
| WSL（产品默认） | `EXECUTOR_UNAVAILABLE (WinError 5)`，可重试 | 作业停在 `queued`，**把 900 秒回合墙钟整体耗光**（任务07 实测 901.6 s） |
| 本机 Docker（未验证后端） | `PRECONDITION_MISSING`，不可重试 | 立刻失败，模型转而用文件路径完成 |

由此得到一条与部署直接相关的结论：**执行器不可用时应快速失败，而不是以可重试错误进入排队**，否则用户看到的是“跑了 15 分钟什么都没发生”，这与最初 300 秒无输出的体验问题同源。当前实现选择可重试，需要单独评估（本轮不改，避免同时变动多个因素）。

结论口径：本环境所有“作业成功”类验收只能记为 `blocked(环境)`，不得用文件路径的结果冒充作业执行。用户正常终端启动的工作台（8769）走 WSL 执行器，不受此限制。

### 3.9 上下文预算：多产品核查任务的真实门槛

任务 11 的五件输入（正射、DSM、LAI、预览 PNG、反演声明）在进入模型前就被拒：

| 项 | 数值 |
|---|---|
| 估算上界 | 28 910 token |
| 允许（32 768 − 4 096 输出预留） | 28 672 token |
| 差额 | **−238 token** |

把账拆开看更清楚：27 个工具 schema 约 16 995 字节、指令约 7 002 字节，两项就是约 24 K token 的固定开销；32 K 窗口在扣掉输出预留后，真正留给用户内容与图片的只剩约 4.5 K。四件产品的视觉预览（约 1 152 token/张）刚好把余量吃穿。

这条直接回答了阶段 A 的第一个问题在“上下文构造”这一侧的答案：**不是模型窗口小，而是固定开销占比过高**。可选处置都属于阶段 3 的架构比较，本轮不动：裁剪工具面、按需分批装载产品、或让栅格走“显式只读引用 + 工具核查”而不是视觉内联。
