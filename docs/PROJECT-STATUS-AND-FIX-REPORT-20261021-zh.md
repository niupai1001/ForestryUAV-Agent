### 2.1 图片为何有token，1024图片实际意味着什么

视觉编码器会把图像转成视觉token；文件的KB大小、像素数量和语言模型窗口不是同一单位。本项目当前Qwen3.5模型配置为16像素patch和2×2空间合并，语言上下文约按32×32像素单元承接视觉表示。[官方模型配置](https://huggingface.co/Qwen/Qwen3.5-27B/blob/main/config.json)支持这一结构。

当前预检对600×600预览估算19×19加128余量，即489；1024×1024预览估算32×32加128余量，即1152。另设256的最小预算，无法确认尺寸的输入保留4096兜底。这些是本应用的预检估算，**不是后端计费token的实测值**，也不是所有视觉模型都适用的通用公式。实际模型usage仍单独记录。

原失败会话的同一600×600图片：旧估算29878，最终代码估算26383，可用输入额度为32768−4096=28672。27个工具Schema最终16995字节、指令7002字节；并不是图片自身占满32K。没有通过抬高上限或修改权重绕过保护。

批量上传只建立文件引用，不把每张图的像素永久放入对话。批图先索引，模型按任务分页选取/读图，使用现有原生压缩与工具结果外置管理历史。100个引用的离线原生工具链已跑通，但这不能替代真实批量理解的质量/性能验收。航片正射重建、几何/空间处理应进入科学Job；普通对话里的图像描述不等于ODM或高分辨率遥感处理。

### 2.2 为什么“卡住”仍是下一优先事项

会话`31c218d5-80c9-4188-8713-f698d3ffede4`的现存事件证明两次请求在300秒预算结束前没有任何原生片段；另一次后续请求确有思考与完整回答。最后失败请求预检估算约7880，远低于28672，不能解释为本次窗口装不下。

只读检查显示Ollama确实加载了大模型，后端窗口262144，而应用保护窗口32768。一次GPU采样为两张RTX5090、各32607MiB总显存，使用31757/32092MiB，利用率89%/79%。这是瞬时观测；当前进程可见性不足以将全部负载归给这个Agent，不能单凭这些数值断言原因。应用未擅自结束其他GPU进程、重启模型或更换权重。

下一步需要把模型排队/加载、提示预填充、首token和生成阶段拆开取证，核对超时后服务端是否仍有推理占用，再决定后端加载窗口/调度调整。只对改变后的实际请求做一次受控核对，保留旧失败与预算，不用更简单问题替换失败目标。

## 4. 删除和自动清理的边界

- 确认删除会话后，清理该会话在当前应用工作区管理的数据；正在执行、有未结清作业或尚在保存模型记录时先停止/等待，不边执行边删。
- 用户上传到应用的副本会删除；路径引用的外部原始文件不删除。其他会话/知识库使用的来源保留；若共享引用指向待删会话自身的文件，先提示解除引用，防止破坏他人输入。
- 旧版没有owner、也没有消息关联的未发送附件不猜测归属；新上传会立即记录owner，避免继续产生同类遗留。
- 新任务终态维护保留正式结果和有界日志，移除退出容器与未被登记为来源的输出副本。用户删除会话时才删除其结果。镜像/卷不做全局prune，现有固定运行时继续可用。
- 本轮先从主工作区移除29个退出容器；其余28个经标签、挂载和Job表核对，属于旧`workspace/runtime`，归档日志后全部移除。旧工作区结果/中间文件按冻结规则保留，未重算。最终带项目Job标签的容器为0。
- 主工作区69个历史Job的容器在本轮前已经不在Docker中、又无归档日志，不能凭空补日志或改写为已核验清理；它们保留待核对事实，不是69个仍在运行的容器。
- 此前另存的开发/用户备份不由会话删除跨目录扫描；本功能不是磁盘安全擦除。显式保存的独立长期记忆/知识库有自己的生命周期。
