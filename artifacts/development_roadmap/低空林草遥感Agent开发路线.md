# 低空林草遥感 Agent：从现有 runtime 到完整系统的开发路线

编制日期：2026-09-05。依据本项目源码、已有研究计划及本次核验的公开论文/官方文档；不依赖 Zotero。本文是开发方案，本轮没有安装新算法、修改已部署runtime或执行数据处理。

## 1. 总体判断与首个交付目标

当前已完成的是文件管理与模型工具调用底座。下一阶段应选一个真实任务，把算法结果、空间位置和业务指标验证清楚，再扩大Agent自主规划能力。

建议首个森林目标：用户上传RGB正射影像和AOI，系统检查输入、识别冠层、计算AOI内有效区域的冠层覆盖度，返回空间结果、指标表与说明。若首要业务是单木调查，则使用实例分割，并加入树冠数量、冠面积与等效冠径。覆盖度和计数需要的标注与算法不同，应先明确业务优先级。

草地的对应目标：RGB或多光谱正射与样方/AOI → 绿色植被、非光合植被/枯落物、裸地等可识别类别 → 分类覆盖比例与斑块图。类别必须根据本地可辨性和标注规则确定。林草完整产品最终要分别验收两个领域，森林先行只是建议的实施顺序。

## 2. 当前位置

| 层 | 已实现 | 后续缺口 |
|---|---|---|
| 交互 | Open WebUI Pipe、附件转发、产物下载 | GIS图层交互、标注修订、项目级视图 |
| 模型 | Ollama调用Qwen3.5:4b、工具定义、最多8轮循环 | 任务契约、能力选择、失败归因、按数据条件规划 |
| 文件 | 磁盘与SQLite资产、owner、asset_id、校验值、父资产ID | 空间资产语义、AOI、同航次/同项目关系、大项目目录结构 |
| 工具 | 7项真实文件工具；TIFF元数据、ZIP、文本、预览 | 空间裁剪/重投影/分块、分割、地理拼接、指标与制图 |
| 知识 | 基础系统提示词 | 来源可追溯的专业资料检索、经验证的处理流程 |
| 执行 | 同步请求、临时结果事件 | 用户已要求暂缓任务状态与日志；长作业阶段再加入 |
| 验证 | 文件/API测试与约32 MiB合成TIFF链路 | 本地林草真值、空间精度、端到端业务测试与跨区测试 |

512 MiB是配置上限，不能推导出GB级项目已可用。当前没有把图像像素送给Qwen做视觉推理，也没有真正的林草分割或NDVI工具。已有8项工程测试通过不等于林草业务精度达标。

## 3. 完整阶段与验收门

| 阶段 | 实际开发工作 | 必须产物 | 进入下一阶段的条件 |
|---|---|---|---|
| D0 需求与指标定义 | 明确用户、森林/草地首任务、输入、AOI、输出和错误容忍度 | 任务说明、指标字典、数据能力矩阵 | 输入和结果可由两位使用者一致解释；每个指标有计算定义和参考依据 |
| D1 数据与基准 | 盘点影像、航次、CRS、波段、GSD、地面/解释标签；按区域/航次分离开发与盲测 | 数据清单、AOI、标注规范、独立测试集、小规模问题集 | 至少有可运行的真实案例及参考结果；不能只有合成图片 |
| D2 空间文件基础 | 为资产添加产品类型/CRS/波段语义/空间范围；实现裁剪、重投影、对齐、切片与拼接 | 可复用GIS工具与小型空间测试数据 | 处理后空间位置正确、NoData正确、重叠边界与面积可复算 |
| D3 单算法与固定流程 | 选一个分割基线，独立运行；处理切片边缘；计算指标；导出GeoTIFF/GeoPackage/CSV | 人工/脚本可重复跑通的领域流程 | 本地验证集达到事先确定的业务阈值；失败类型有解释 |
| D4 Agent编排 | 将稳定流程/工具封装；解析目标、AOI、数据条件；工具选择、参数校验、结果解释 | 自然语言驱动的森林或草地完整小任务 | 同输入下与固定流程结果一致；缺条件时选择补充、降级或明确不可做 |
| D5 专业知识与程序知识 | 整理术语、规范、仪器/算法说明、论文和经过验证的SOP；建立检索工具 | 引文可定位的知识检索、工具适用规则 | 回答能追溯资料；规则能检查计算前提；检索没有替代真实测量 |
| D6 长作业与原始照片 | 再加入作业状态、参数版本记录、防重复提交；接EXIF/POS质检、ODM/NodeODM、产品检查 | 原片到正射/DSM的受控流程、任务恢复基础 | 页面断开不丢作业；可查原作业；重试不重复重建；产品精度有验证 |
| D7 跨区与林草扩展 | 独立地区/季节/GSD测试；加入另一个领域；有条件再做多光谱/CHM/变化分析 | 外部测试报告与第二领域插件 | 两个领域分别通过验收；明确哪类场景不能支持 |
| D8 模型优化 | 根据错误来源选择视觉微调、提示/工具说明改进、检索优化、语言模型升级或SFT | 对照实验、可重现模型配置 | 对盲测有稳定收益，而不是仅改善示例回答 |
| D9 产品发布与迭代 | 固定版本、安装/升级/备份、用户权限、资源限额、项目与地图交互、反馈回归 | 可安装版本、使用手册、评测与模型/工具版本清单 | 他人能在目标环境复现核心结果，并识别超出适用范围的输入 |

D1评测建设贯穿全程；D5资料整理可与D2–D4并行。D6不能仅靠更长HTTP超时完成。阶段按验收门推进，不在未知人力和数据条件下承诺日历工期。

## 4. 每个任务应该长什么样

用一个小型“任务契约”表达用户需求，无需先实现复杂规划语言：

```yaml
task: canopy_cover
inputs:
  orthomosaic: asset_x
  aoi: asset_y
target: 可见树冠的平面投影覆盖
denominator: AOI内具有有效影像的区域
outputs: [canopy_mask.tif, metrics.csv, report.md]
conditions:
  band_semantics: 已确认的RGB
  spatial_reference: 可用于相应空间计算
```

实际运行前检查：AOI与影像是否相交、CRS能否转换、像元单位、影像是否已经正射、波段含义是否已确认、算法GSD适用范围、空数据和NoData是否正确处理。TIFF后缀不代表正射产品，3个波段也不能自动证明RGB。

覆盖度计算应由代码实现：在已定义有效区域内计算树冠掩膜的面积比例，避免重叠多边形重复计数；同时报告AOI缺测比例。不同坐标系/像元尺度下应采用适合的面积方法。仅有目标检测框不能直接代替真实树冠面积。

若业务要求每木参数：明确林缘截断冠、遮挡冠、多主干和重叠冠的计数规则。可见冠数量不必然等于地面全部树木数量。RGB冠幅与树高、胸径、蓄积量分别需要不同证据；DSM不是直接树高，CHM计算还要求适用的DTM与空间/垂直基准一致。

## 5. 工程实现路线

### 5.1 保留现有底座

继续沿用Open WebUI→Pipe→FastAPI runtime→Ollama。先在现有代码边界扩展，不因为将来可能复杂就重写全部框架。

短期在`storage.py`增加最少必要的空间属性；在`tools.py`补GIS工具和一个稳定业务工具。工具多到难维护时再拆为`tools/raster.py`、`tools/forest.py`、`tools/grassland.py`。模型循环仍由`agent.py`控制。

资产字段可逐步向STAC的时空与资产描述方式靠拢，优先借用字段，不必先搭完整STAC服务。[STAC官方规范](https://stacspec.org/en/about/stac-spec/)

### 5.2 第一个算法选择

- 林冠覆盖任务优先比较一个语义分割基线与简单基线。
- 单木冠边界任务可用detectree2作候选实例分割基线；它基于Mask R-CNN，有公开代码与训练流程，是否适合本地林型需验证。[detectree2官方仓库](https://github.com/PatBall1/detectree2)
- 草地覆盖可从小型U-Net类语义分割基线开始；已有UAS研究分别比较RGB、多光谱及绿色植被/非光合植被/裸地覆盖任务。[Sotomayor等，2025](https://doi.org/10.1007/s10980-025-02193-y)

先固定算法和输入要求，再允许模型选参数。LLM选择“冠层覆盖流程”即可，重投影、切片、拼接等确定步骤可以由程序控制，不必每一步都要求4B模型重新推理。

### 5.3 知识与模型优化

把能力建设拆开：

| 现象 | 优先改哪里 |
|---|---|
| 专业概念答错或缺来源 | 术语/规范检索、引用定位、问答评测 |
| 选错工具或缺必要参数 | 工具说明、任务契约、硬前提检查、候选工具筛选 |
| 树冠分割不准 | 输入分辨率/颜色/季节检查、本地标注、视觉模型适配 |
| 面积或空间位置错 | CRS、仿射变换、NoData、拼接、确定性计算 |
| 长任务断开或重复提交 | 作业生命周期、恢复与防重复机制 |
| 4B仍不能稳定执行合法流程 | 在同一工具/数据集下比较更强模型，再决定升级或语言SFT |

专业资料需要存成“可定位的证据片段”，保留题名、年份、页码/章节和适用条件；执行SOP则保留前提、步骤、参数与检查项。资料检索服务可以独立于界面。首版无须先引入知识图谱、多个向量数据库或多Agent。

视觉模型微调与语言模型微调是两条不同路线。视觉微调依赖本地标注；语言SFT依赖人工检查过的任务—工具—参数—结果轨迹。错误结果不能自动变成训练样本。知识库接入不会改变Qwen权重。

### 5.4 原始照片与计算资源

当已有正射流程可靠后，接入原片：文件按航次/相机/时相组织 → EXIF/POS与质量检查 → 摄影测量 → 正射/点云/DSM质量检查 → 复用D3–D5业务流程。NodeODM提供航测处理的REST入口，可作为适配对象。[NodeODM官方仓库](https://github.com/OpenDroneMap/NodeODM)

工程规模扩大时优先让大原图留在文件/对象存储，聊天只传资产引用；采用分块读取和预览，而不是继续扩大Base64消息。原片项目需要保留目录和sidecar关联，当前ZIP逐成员登记方式需要在这一阶段扩展。

现有2026-09-03盘点记录包含120张RGB照片、80张多光谱文件（20组四波段），日期与区域不同；可作为两组独立工程候选，不能直接拼成一个项目或当成同地多时相变化样本。这只是既有盘点信息，未在本轮重新检查数据是否仍可访问或有足够真值。

## 6. 评测方案：开始就做，规模逐步扩大

初期可准备50–100条人工核对的开发题，作为工作量建议而非统计充分性声明：正常任务、缺波段/缺CRS、模糊意图、跨文件依赖、工具失败分别覆盖。开发样例与最终盲测分开；按地区/航次分组，不能让同一正射的相邻切片跨训练和测试。

| 评价层 | 核心检查 |
|---|---|
| 文件/工具 | 数据读写正确、引用可访问、参数有效、产物确实存在 |
| 空间 | CRS和单位、地理位置、裁剪范围、有效像元、切片边缘与面积 |
| 视觉 | 语义分割IoU/F1；实例分割对象匹配/边界与计数误差；按林型/GSD分层 |
| 业务指标 | 覆盖度绝对误差用“百分点”；冠面积、计数等与相应参考比较 |
| Agent | 工具和参数是否合适、任务完成率、错误继续/无谓拒绝、调用次数、耗时 |
| 专业回答 | 数字能否追溯结果、引用是否支持结论、是否越过数据能力边界 |

固定流程、直接LLM、LLM+工具、LLM+工具+领域前提/知识是基础对照。使用相同算法与数据，才能分清Agent改进和视觉模型改进。轨迹不必逐字匹配唯一专家路径，应接受终值等价且条件成立的流程。

ThinkGeo提供分步骤和最终答案的评价思路；当前v3是486任务、1778个专家核验步骤，旧项目笔记的436需按引用版本更新。[ThinkGeo原文](https://arxiv.org/abs/2505.23752v3)

Earth-Agent官方实现同时评估工具/参数轨迹与最终结果，可借鉴评价器结构；其EO基准并不直接证明UAV重建或林草指标可用。[Earth-Agent官方实现](https://github.com/opendatalab/Earth-Agent)

## 7. 有价值的新增研究方向

下列是待验证假设，不是已经证明的创新或本轮待实现清单。

| 优先级 | 方向 | 可验证问题 | 最小对照 |
|---|---|---|---|
| P1 | 空间与数据条件约束下的工具选择 | 明确波段语义、CRS、产品类型和GSD，是否减少“调用成功但科学上不成立”的结果？ | 普通JSON工具描述 vs 增加领域前提与自动检查 |
| P1 | 从分割误差到林草指标误差的传播 | 像素分割分数提高是否一定改善覆盖度/单木计数？何时应报告不确定性或要求复核？ | 只报告模型分数 vs 加入空间/业务质量检查 |
| P1 | 跨样地可迁移流程 | 保持runtime相同，仅更换视觉模型/参数，能否迁移到另一林型或草地？ | 本地随机切片测试 vs 独立地区/季节测试 |
| P2 | 分辨率与计算预算选择 | 自动选择切片大小/分辨率能否降低成本，同时保持业务误差？ | 固定分辨率 vs 预算约束策略 |
| P2 | 失败后局部恢复 | 在工具失败或质量不足时能否只重跑必要步骤？ | 全部重跑 vs 持久化状态与局部重规划 |

OAM-TCD可作为树冠/树覆盖外部数据候选，仍需要核对任务标签与本地UAV数据差异。[OAM-TCD](https://arxiv.org/abs/2407.11743)

CangLing-KnowFlow可作为程序知识和重规划的后期研究参考；本次核验的是预印本，当前无需为了对齐其叙事实现自演化或多Agent。[CangLing-KnowFlow](https://arxiv.org/abs/2512.15231)

如果需要持久化编排，可评估LangGraph等框架的检查点机制；是否迁移取决于实际复杂度，现有工具与存储接口可保留。[LangGraph持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence)

## 8. 下一轮的明确开发清单

1. 选一份真实RGB正射和一个小AOI，冻结“冠层覆盖”或“单木调查”首任务；准备一份人工参考结果。
2. 加入AOI识别、空间裁剪与切片，验证CRS、NoData与位置保持。
3. 接一个分割基线，在Qwen之外跑通“影像→掩膜/冠多边形→指标→文件”。
4. 将该流程封装成一个明确业务工具，再让Qwen根据目标和数据条件调用。
5. 建立第一组正常、缺信息与失败案例，同时整理少量直接支持当前流程的专业资料。

在上述小任务仍可同步完成时继续暂缓任务状态与执行日志。首次引入长时重建、长时大图分割、并发用户或恢复实验之前，再将它们作为明确工作包加入。

六项核验资料已整理成同目录的`development_references.ris`，未与任何私人资料库去重。来源范围覆盖规划评测、森林视觉、草地覆盖与后期恢复，并非全面文献综述。
