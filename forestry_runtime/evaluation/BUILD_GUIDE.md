# Agent 评分系统框架制作说明

版本：v0.1

编制日期：2026-09-19

适用项目：低空林草无人机遥感通用 Agent
对应评价协议：`forestry-eval-0.1`

本文说明本次评分框架的设计目的、制作过程、文件组成、数据流、计分实现和后续接入方法。内容以当前仓库为准，供项目维护者、评价执行者和结果审核者使用。

当前交付是**评价规则、任务契约和离线计分器**。真实模型执行采集、独立领域验证、浏览器观测和正式基线还需要按任务接入。本说明中的演算数字只用于解释规则，不是项目实测得分。

## 一、制作目标与设计依据

评分系统要回答三个研发问题：系统在哪些任务上能够正确交付；失败发生在哪个环节；一次改动是否在相同条件下改善了结果。

此前项目已有工程测试、真实 Qwen 烟测和运行日志，但三者的判定对象不同。工程测试可以证明特定状态转换正确；模型调用某个检查工具可以证明工具协议走通；HTTP 两轮成功可以证明接口链路可用。它们分别都不能代表整个 Agent 的业务成功率，也不能替代浏览器中的消息显示验收。

制作时先核对这些已有材料，再将用户提供研究中的方法转化为本项目规则：

| 设计选择 | 制作理由 | 在本框架中的体现 |
|---|---|---|
| 结果与过程分开 | 合理的调用过程仍可能得到错误结果 | 完整任务成功率为主指标，过程错误用于诊断 |
| 按交付物验证 | CSV、栅格和知识回答的正确性定义不同 | 每题冻结独立检查项 |
| 门禁独立 | 权限、重复副作用等问题不能被平均分掩盖 | 门禁失败时报告 blocked |
| 重复运行 | 一次成功不足以说明稳定完成能力 | agent 每题固定运行三次 |
| 允许等价实现 | 固定工具名会惩罚有效的自主代码方案 | 判结果、约束和必要证据，不要求唯一工具顺序 |
| 缺证据显式保留 | 删除未测或失败案例会抬高成功率 | 固定分母、unknown、覆盖率和缺证据上下界 |

研究来源与采纳边界记录在 [FRAMEWORK.md](FRAMEWORK.md) 第 1 节。本版没有引入十维主观加权总分，也没有制定未经项目数据校准的“80 分合格线”。

本框架所说的客观，是规则提前明确、证据可以检查、计算可以复现。题目选择、容差和应用风险仍需领域判断，必须公开其来源并维护版本。

## 二、制作范围与文件职责

遵循项目的范围约束，评价代码放在现有 `evaluation/` 下，复用 Runtime 已有运行记录。评价器不参与 PydanticAI 模型循环，也不改变模型的工具选择。

```text
evaluation/
  FRAMEWORK.md       评价协议：为什么这样评、什么才算通过
  suite.json         任务契约：测哪些任务、每题必须验证什么
  scorecard.py       离线计分：校验记录、聚合结果、输出报告
  README.md          运行命令和证据包格式
  BUILD_GUIDE.md     本制作说明
tests/
  test_evaluation.py 计分规则与反例测试
```

这些文件各自只有一个必要职责。`suite.json` 的任务描述不是执行器；`scorecard.py` 不是自动科学裁判；`test_evaluation.py` 测的是计分逻辑，不是真实 Qwen 的能力。

## 三、评价对象与任务编排

### 3.1 三条独立轨道

| 轨道 | 评价对象 | 证据要求 | 本版安排 |
|---|---|---|---|
| agent | 真实模型完成任务的能力 | 真实模型执行、运行记录、交付物和独立验证 | 12 题 × 3 次 = 36 个槽位 |
| engineering | Runtime 的关键工程约束 | 故障注入、SQLite、文件或容器实态 | 4 题 × 1 次 = 4 个槽位 |
| ui | 用户看到和操作的界面 | 真实浏览器、DOM/截图、网络与时间记录 | 2 题 × 3 次 = 6 个槽位 |

总计 18 个基础任务、46 个预定试验槽位。槽位指一条预定评价记录，并不等于一次 HTTP 请求；多轮任务和带正反例的任务可以包含多个子场景。

engineering 可以使用可控 mock 测异常分支，但沙盒隔离等需要真实容器证据。ui 可以使用受控后端隔离前端问题，仍必须有浏览器观测。三条轨道不混算总分。

### 3.2 本版任务目录

| 分组 | 任务 ID | 要验证的核心结果 |
|---|---|---|
| 通用执行 | core.paths | 精确路径、目录范围与文件清单正确 |
| 通用执行 | core.csv | 按业务键汇总准确，交付表与回答一致 |
| 通用执行 | core.repair | 观察真实脚本错误，修改后实际执行成功且结果正确 |
| 通用执行 | core.changed_input | 输入改变后真实重跑，新结果关联新作业 |
| 林业 UAV | forestry.inventory | 主航线、参考板、既有成果分开，数量与范围准确 |
| 林业 UAV | forestry.product_qa | CRS、单位、网格、波段、掩膜与质量边界准确 |
| 林业 UAV | forestry.chm | 条件充分时生成正确 CHM，条件不足时说明缺口 |
| 林业 UAV | forestry.ndvi | 波段与缩放使用正确，像元、掩膜和统计可核对 |
| 知识/上下文 | knowledge.support | 引用支持结论，无依据问题不编造答案 |
| 知识/上下文 | knowledge.optional | 需要时检索，不需要时直接正确回答 |
| 知识/上下文 | knowledge.memory | 遵循显式项目记忆，正确处理修改、删除和项目隔离 |
| 知识/上下文 | knowledge.context | 真正压缩后仍保留目标、约束、错误与未完成子任务 |
| 工程门禁 | gate.permissions | 合法读取成立，未授权访问与写源受阻 |
| 工程门禁 | gate.sandbox | 普通执行离线，联网安装不挂载源数据 |
| 工程门禁 | gate.idempotency | 输入重传和不确定提交不重复产生副作用 |
| 工程门禁 | gate.recovery | 恢复、暂停、取消反映真实执行状态 |
| UI | ui.send | 自己的消息及时可见，列表刷新不清空对话 |
| UI | ui.reconnect | 长事件流、刷新和重连后历史及终态正确 |

每题的 `goal`、`fixture`、`checks` 以 [suite.json](suite.json) 为准。目前 fixture 字段说明需要什么输入，尚不代表该题全部样本和采集器已制作完成。

## 四、工作流与证据边界

```text
冻结任务契约和环境配置
        ↓
按轨道运行任务，采集事件、文件或页面证据
        ↓
独立验证器对照真值判断每个必需检查项
        ↓
生成 records.json 与对应证据文件
        ↓
scorecard.py 检查版本、配置、轨道和重复槽位
        ↓
判定各次试验 → 各任务 → 各能力组
        ↓
输出门禁、得分、覆盖率、未知项和逐题原因
        ↓
定位优先修复任务，再做同条件版本比较
```

本流程中，**采集、判断与聚合是三件事**：

1. 采集器记录发生了什么，例如完整事件、Job 退出码、下载产物、用户气泡首次显示时间。
2. 独立验证器判断是否满足任务，例如逐键比对 CSV、检查 CHM 数值和网格、审核引用是否支持声明。
3. 计分器汇总验证结果，不重新执行模型，也不凭回答措辞推断正确。

标准答案、验证器和证据包应由评价端管理，放在被评 Agent 不能写入的目录中。知识检索也不能访问隐藏标准答案。

现有计分器检查证据路径位于证据包目录内、文件存在且标有 verifier；它**没有验证证据内容真伪，也没有实现证据目录的运行时访问隔离**。这些由后续采集器部署、验证器审查和环境权限落实，不能仅凭一个文件存在就宣布证据可信。

## 五、任务契约和运行记录怎么制作

### 5.1 制作任务契约

每题至少明确任务 ID、轨道、分组、用户目标、测试输入和必需检查。只有确实属于发布阻断条件的任务才标记 `gate: true`。

编写检查项时，应描述可验证的结果。例如“所有业务键及汇总数值符合独立真值”，比“调用 csv 工具成功”更能代表用户目标。工具协议专测可以要求某个工具，但应标明其测试性质，不混入自主选法成功率。

实际执行前还要补齐并冻结样本版本、数值容差、资源预算、时间限制、故障注入点与允许修改范围。现在的任务目录尚未逐题固定全部这些值，因此正式采集之前仍有准备工作。

### 5.2 制作运行记录

`records.json` 顶层为数组。每条记录代表一个任务的一次预定重复，主要字段如下：

| 字段 | 制作要求 |
|---|---|
| suite_version | 与任务目录版本完全一致 |
| case_id | 对应已登记任务，不能临时增加题目 |
| track / execution | 标明轨道和真实执行性质，禁止把 mock 标为真实模型 |
| repeat | 预定重复编号，从 1 开始 |
| trial_id | 证据包中唯一的试验标识；不代替 Runtime Run ID |
| configuration | 冻结源码、模型、Prompt、工具、数据、环境、验证器、采样和预算 |
| status | evaluated、timeout、crash、infra_error 或 verifier_error |
| status_evidence | 证明试验终态或失败状态的文件与验证器版本 |
| checks | 与契约对应的 verdict、verifier 和 evidence |

配置的九个必填字段是 `code_snapshot`、`model_digest`、`prompt_snapshot`、`tools_snapshot`、`dataset_version`、`environment_snapshot`、`evaluator_version`、`sampling`、`budgets`。同一轨道同一报告中的 configuration 必须完全一致；更换配置另出报告。

实际 Run、Turn、Action、Job、Artifact ID 应保存在证据文件中，使审核者能找到原始记录。完整格式示例见 [README.md](README.md)，其中占位字符串不能作为真实配置快照使用。

## 六、计分算法及实现细节

### 6.1 每次运行的判定顺序

现有 `scorecard()` 按以下顺序执行：

1. 验证任务目录、版本、轨道、执行类型、重复编号和配置字段。
2. 拒绝重复 trial_id、重复任务槽位、超出计划的重复次数、未登记检查项和混合配置。
3. 对每个必需检查核对 verifier 标识与证据文件。缺项或缺证据转为 unknown。
4. 任一有证据的检查失败，该次试验为 fail。
5. 否则，若有终态证据证明 timeout/crash，该次试验为 fail。
6. 否则，仅当 status=evaluated、终态证据有效且全部必需检查为 pass 时，该次试验为 pass。
7. 其余情况为 unknown，保留在预定分母内。

`evaluated` 是评价端确认已到达契约要求终态，不等于 Runtime 必须显示 completed。正确报告缺数据、拒绝越权或按要求安全暂停，都可能符合任务契约。

### 6.2 分数、覆盖率和上下界

对一个任务，计划运行次数为 N，已验证成功为 P，已验证失败为 F，未知为 U，满足 N=P+F+U。

```text
完整得分 = 100 × P / N                 仅 U=0 时给出
证据覆盖率 = (P + F) / N               输出范围 0～1
缺证据下界 = 100 × P / N
缺证据上界 = 100 × (P + U) / N
```

能力组按任务成功率平均；当前每组每题重复次数相同，因此实现中合并该组槽位计算，与逐题等权平均一致。agent 主分是 core、forestry、knowledge_context 三个组的等权平均，不包含 engineering 和 ui。

只有三组证据齐全时才输出 `agent_macro_score` 和 `worst_agent_group_score`。门禁或 UI 尚未齐全时，agent 主分可能已经可计算，但整体 qualification 仍为 incomplete；二者含义不同。

`all_repeats_success_rate` 表示组内“每次重复都成功”的任务比例。它不是至少成功一次的 best-of-N，也不是总体可靠性的置信下限。当前 `confidence_interval` 固定为 null，bootstrap 和配对统计尚未实现。

### 6.3 演算示例

假设三个 agent 组各有 12 次运行，全部已有证据：通用执行 8 次成功、林业 UAV 9 次成功、知识/上下文 10 次成功。

| 指标 | 演算值 |
|---|---:|
| core | 66.67 |
| forestry | 75.00 |
| knowledge_context | 83.33 |
| agent_macro_score | 75.00 |
| worst_agent_group_score | 66.67 |

这个结果表示在本套固定试题上，三个能力组等权后的完整成功比例为 75%，不能直接解释为“任何林业任务有 75% 成功概率”。

另一种情况：某组 12 次中 7 次成功、3 次失败、2 次未知。正式分数为 null，覆盖率为 10/12≈83.33%，缺证据范围为 58.33～75.00。该范围表达未获得证据可能造成的分数变化，不是统计置信区间。

### 6.4 门禁和发布状态

| 输出 | 代码中的含义 |
|---|---|
| gates=fail | 至少一个门禁存在已验证失败 |
| gates=pass | 所有已登记门禁的预定运行全部通过 |
| gates=unknown | 尚不足以判断全部门禁通过 |
| qualification=blocked | 门禁已发现失败，优先处理该阻断 |
| qualification=incomplete | 证据未齐，或门禁尚未确定通过 |
| qualification=measured_unqualified | 全部测量完成且门禁通过，但本版尚未定义经过校准的发布合格线 |

因此即使 agent 主分是 100，也可能由于门禁失败而 blocked。另一方面，`measured_unqualified` 不是“系统已被认定不合格”，而是“测量完成、尚未作发布资格判定”。

### 6.5 数值容差辅助函数

`numeric_check()` 对已经统一单位的有限数值执行：

```text
绝对误差 = abs(actual − expected)
有效容差 = max(abs_tol, rel_tol × abs(expected))
通过 = 单位相同 且 绝对误差 ≤ 有效容差
```

当前实现以单位字符串相等为准，不自动把厘米换成米；需要时由独立验证器先进行有依据的单位归一化。NaN、无穷、布尔值、缺失数值以及负容差会被拒绝。

这个辅助函数可以被领域 verifier 调用，但 `scorecard()` 不会自动对所有文件执行数值验证。CRS 语义等价、完整掩膜、GeoTIFF 网格和引用支持关系，需要各自的验证器实现。

## 七、使用和验证方法

在 `forestry_runtime` 目录执行：

```powershell
# 查看无记录时的任务覆盖与缺失清单
python evaluation/scorecard.py

# 对评价端已制作的真实证据包计分
python evaluation/scorecard.py --records evaluation/work/baseline/records.json

# 验证计分器的规则和反例处理
python -m pytest -q tests/test_evaluation.py
```

计分器向标准输出打印 JSON，不启动模型、不修改正式会话数据。正常业务状态的退出码：0 表示完整测量；1 表示门禁阻断；2 表示证据不完整。

格式或契约校验失败目前会抛出异常并输出错误，尚未封装成统一 JSON 错误报告。因此自动流水线不能只凭退出码 1 就认定“门禁失败”，还应检查是否输出了有效 scorecard 及其 qualification。

本次框架制作时，9 项计分器测试、4 个子测试通过，覆盖缺证据、缺终态、门禁阻断、重复槽位、错用轨道、配置混杂、超时、数值单位及非有限值。它们只证明这些计分分支的行为符合设计。

现阶段不提供 records 时的实际报告是 incomplete，主分 null，18 个任务的证据尚未按新协议录入。历史工程测试与 Qwen 烟测继续作为回归资料，不能直接补成新协议下的正式分数。

## 八、后续制作与维护规则

| 顺序 | 制作内容 | 完成判据 |
|---|---|---|
| 1 | 样本与独立真值 | 每题输入、容差、预算、gold 版本齐全，Agent 无法读取隐藏答案 |
| 2 | 独立 verifier | 已知正确样本通过，典型错误、缺失结果、伪引用等反例失败 |
| 3 | API 和浏览器采集器 | 保存完整事件/产物/页面观测，能生成可定位的 records.json |
| 4 | 固定基线 | 按预定 46 个槽位运行，所有结果保留；环境故障明确标记 |
| 5 | 泛化与比较 | 新地块/日期 holdout、固定配置 A/B、配对差与统计不确定性 |
| 6 | 发布政策 | 根据实际失败成本和使用场景校准各组下限、关键错误与延迟要求 |

新增任务前先确认它测量的能力及真值来源；不能在看到结果后删除难题或放宽容差。改变检查、输入、重复次数或配置，应升级对应版本并分别报告。修复后的重跑属于新版本实验，不能覆盖旧版本失败。

同一地块的多个文件和同一道题的近义改写应作为相关样本处理。当前计分器没有任务簇字段和簇内聚合实现，扩展任务变体时应先补这项机制，避免简单地添加大量近似题改变分组权重。

研发优先级依据具体失败案例排序：先处理门禁和交互阻断，再处理最差能力组的主要失败，最后优化正确任务的延迟与成本。主分用于观察整体变化，逐题证据用于决定改哪段代码。
