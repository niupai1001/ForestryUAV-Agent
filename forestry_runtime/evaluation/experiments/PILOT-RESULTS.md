# 能力开关对照实验：试点内容、结果与复盘

日期：2026-09-27/28 · 考题：oam-07 × 每组合 2 遍 × 8 种组合 = 16 次
本报告用白话写，技术细节放在括号里。

---

## 一、这次实验做了什么？

**考题（oam-07）**：给 agent 一张树冠掩膜图（GeoTIFF，有树冠的地方像素非零），
要求它统计三个数——树冠覆盖率百分数、树冠像元数、总有效像元数——并写成 JSON 交付。
题目自带标准答案和容差，判分器能自动打分（全对得 1 分，否则 0 分）。

**怎么测**：模拟真实使用。向运行中的 agent 服务发这道题，agent 自己决定怎么做——
看文件、读领域指南、写 Python 代码跑统计（rasterio/numpy）、或直接写答案文件。
全程记录每一步：模型被调用了几次、用了哪些工具、花了多少 token、最终是否正常收尾。

**只改三个变量，其他全部锁死**：

| 变量 | 取值 |
|---|---|
| 能力开关（检索/子代理/并发） | 关（默认）/ 开 |
| 上下文窗口 | 32K / 128K |
| 模型 | qwen3.5:4b（小）/ qwen3.8:27b（大） |

三种变量组合出 8 臂（E1–E8），每臂跑 2 遍。开关是容器级环境变量，
跑"关"的组合时重建容器并**逐键核对容器里的真实开关状态**——
首轮试点曾因开关状态标错导致整批数据作废，这次没再发生。

## 二、实验结果靠不靠谱？

**靠谱。16/16 次全部通过有效性核验**：

- 标了"关"的 4 臂：trace 里没有任何检索信号，工具清单 27 个；
- 标了"开"的 4 臂：每次请求都带检索结果（fused 模式），工具清单被检索路由
  削减到 25 个（含子代理入口 delegate）；
- 上下文窗口精确等于设定值（32K/128K），模型版本精确等于设定值。

## 三、八臂结果

（calls = 模型被调用次数；tok = 累计输入 token；n=2 只能看方向）

| 组合 | 开关/窗口/模型 | calls | 输入 tok | 结果 |
|---|---|---|---|---|
| E1 | 关/32K/4b | 8.0 | 122K | 2 遍都正常收尾 |
| E2 | 开/32K/4b | 11.0 | 161K | 2 遍都正常收尾 |
| E3 | 关/128K/4b | 19.0* | — | 1 遍正常，**1 遍复读卡死（见四）** |
| E4 | 开/128K/4b | 15.5 | 300K | 2 遍都正常收尾 |
| E5 | 关/32K/27b | 8.0 | 139K | 2 遍都正常收尾 |
| E6 | 开/32K/27b | 9.0 | 154K | 2 遍都正常收尾 |
| E7 | 关/128K/27b | 6.0 | 98K | 2 遍都正常收尾 |
| E8 | 开/128K/27b | 4.5 | **58K** | 2 遍都正常收尾，最省 |

*E3 的均值被复读那次拉高（33 次 vs 5 次）。

**方向性结论**：

1. 最省的组合是 **27b + 128K + 开关开**：比开关关省 41% 输入 token、少 25% 调用。
   大模型给足上下文后，检索证据让它一两次就做对。
2. 32K 窗口下开关开反而略贵 10–32%（检索结果本身占 token）。
3. 一个意外发现（后已查明根因并修复）：16 次 trial 的计时器全部"超时"，但其中
   15 次的 agent 其实早就正常完成了。最初猜测是"排队+模型加载花掉 790 秒"，
   精确复盘推翻了这个猜测——**agent 干活只要 115–260 秒，多出来的 ~775 秒是
   完成事件之后采集器在空等一个永远不会来的状态翻转**（完成事件的用词 "done"
   与状态机的合法用词 "completed" 不一致，状态机拒绝这个转移，Run 的记录就
   永远停在"运行中"）。修复后实测同一个题从 ~910 秒降到 **175.8 秒**，
   且自动打分链路打通（详见第六节）。

## 四、E3 为什么会反复写同一个文件？（重点复盘）

**现象**：E3（关/128K/4b）第 1 遍里，agent 正常探索了 10 步（看图、读指南、
列目录），然后开始写答案文件 `analysis/oam-07-input_analysis.json`——
接着**把同一个文件、同一份内容连写了 19 遍**，直到 32 轮上限被强制暂停。

**证据链（逐条查过）**：

1. 19 次写入路径相同、内容哈希（md5）完全相同——不是在改内容，是逐字复读。
2. 每次写入工具都返回"成功"。不是工具报错逼它重试。
3. 历史没有被压缩丢弃：对话历史从 1 条涨到 65 条，输入 token 从 13.5K 涨到
   46.6K，"我已经写过了"的证据全都还在历史里。
4. 19 轮里 16 轮模型生成的回复**一字不差**（指纹比对）。

**白话解释**：qwen3.5:4b 这个小模型在很长的对话里"跟丢"了。它每轮看到的
最近内容都是"该写这个文件"，于是又写一遍。温度设的是 0.2（几乎确定性），
同一个输入几乎必然产出同一个输出，于是一旦进入复读就没有东西能把它推出来。

**这暴露的真正缺口**（你说得对，轮次上限只该是最后防线，不能当日常兜底）：
现有的软反馈只覆盖两种重复——"重复的**失败**调用"（每次带理由拒绝）和
"重复的**读取**"（第二次起回复带 already_read 标记）。**"重复的成功写入"
没有任何软反馈**——写一遍是成功，写十九遍也每次都是成功，系统一句话都不多说。
这才是轮次上限被迫出场的根本原因。

**建议的修法**（小改动，不恢复任何硬暂停）：在观察账本里检测
"本次调用的工具名 + 参数与之前某次完全相同"，从第二次起在返回结果里附一句
"这是对第 N 次调用的逐字重复，结果不会变化"。不拒绝、不暂停，只让模型看见。
复读自然就断了。另外可评估复读诊断触发时临时调高温度。

**E4（开/128K/4b）为什么没复读**：它采样走了另一条路——写代码跑统计
（code_run×7 + 等作业×6）。代码路线每轮都有新信息（作业输出、报错、数据），
模型在"改代码→看结果→再改"的闭环里，复读没有形成条件。要诚实说明：
这是 1 遍对 1 遍的行为分叉，**不能断言是开关让 E4 收敛**；合理的假设是
开关开的检索段每轮给上下文注入了额外锚点，让小模型不容易跟丢，但试点样本
证明不了这一点，需要完整实验检验。

## 五、子代理开关为什么这次检验不了？

不是测试设计漏了它，是**这道题触发不了它**。子代理（delegate）设计上有三种用途：

1. `explore`——只读调查（比如"把这三个数据目录都摸一遍再回来汇报"）；
2. `environment`——装依赖、诊断执行环境；
3. `verifier`——独立核验已有产物。

oam-07 一张图、三个数、单份 JSON 产物，rasterio/numpy 在环境里早就装好，
主 agent 一个人就能干完——没有任何"派小弟"的收益场景。
所以 8 臂里 delegate 调用次数全是 0，是符合预期的正常现象。

**要检验子代理开关，需要换/加这一类题**：多输入需要并行调查的、
环境缺依赖需要安装的、多产物需要互相核验的。下一步选完整实验的 14 题
时，确认题库里是否覆盖这三类场景；没有的话需要补题。

## 六、局限与下一步

1. 每组合只跑 2 遍，同组合内波动很大（最多差 28 倍调用数），本报告只给方向。
2. 打分（判分器）这次全部缺失——根因同上（完成事件用词与状态机不一致，
   Run 记录永卡"运行中"，采集器等到超时，判分器没机会跑）。**已修复并验证**：
   coordinator 加了事件词→状态机词的映射，重建镜像后实测 fixcheck/r9——
   agent 干活 175.8 秒、终态正确落盘、采集器立即收尾、判分链路打通。
   完整实验可以直接跑，不需要加大 timeout。
   判分首跑还带来一个诚实的新发现：r9 那次 4b 模型"自称完成"但**没有交付
   题目要求的统计 JSON**（artifact_present=fail，只交了预览图）——修复前
   这类 trial 记为超时、无法区分"真完成"与"自称完成"；修复后判分器第一次
   能把两者分开。这正是 M1 判分存在的意义。
3. 复读软反馈（第四节）建议先修再跑完整实验：14 题 × 3 遍 × 8 组合 = 336 次，
   4b@128K 组合很可能再出复读，修了能省大量废跑。
