# 本项目评价协议 v0.1

状态：研发试行规范与离线计分器已建立；固定任务的采集器、独立 verifier 和盲测集尚未全部接入，当前不发布 Agent 总分或生产认证。适用目标：Windows + Docker 单用户通用 Agent，以及可关闭的低空林草遥感能力。摄影测量部署、卫星分类、大气模拟不进入本版分母。

## 1. 研究中采用什么

| 参考 | 本版采用 | 不直接采用 |
|---|---|---|
| [Earth-Agent 官方评价实现](https://github.com/opendatalab/Earth-Agent) | 结果与工具轨迹分开观察 | exact tool sequence 作为任务成功条件 |
| [TerraBench v1 §4.3、附录 D/E](https://arxiv.org/html/2606.13148v1) | 单位与容差；过程、数值结果分离；配对比较 | 把其工具权重直接当成本项目最优权重 |
| [GISclaw 官方说明](https://github.com/geumjin99/GISclaw) | 按产物类型验证；复现实验固定版本 | 使用变化中的 main 分支复现论文数字 |
| 用户提供的研究报告 | 门禁、能力分组、重复实验、故障分类 | 十维 25/15/15… 权重、70/80/90 等级作为客观标准 |

上述链接于 2026-09-19 核验；GISclaw 官方说明明确区分当前应用与论文冻结实现。报告中的内部 citation 标记不是可直接追溯的书目。本版只依赖上表已核验的方法，不使用尚未逐项复核的 AUC、排行榜数字来证明本项目能力。

“客观”指相同证据与相同规则可以复算出相同判断，不代表任务选择、容差和业务风险偏好没有人为决策。这些决定必须在运行前公开、版本化，并用失败案例校准。

| 当前材料 | 能证明什么 | 还不能证明什么 |

| tests/ 中状态、权限、恢复、数值测试 | 明确条件下的工程不变量与工具实现 | 真实模型自主完成率、用户交互质量 |
| `scripts/legacy_verify_qwen_uav_rag.py` | 真实 Qwen 的定向能力烟测 | 自主选法、独立结果真值、重复稳定性 |
| 上述脚本的 inventory/chm 检查 | 指定工具返回角色/缺失项 | 最终文字是否准确复述、无遗漏或矛盾 |
| knowledge 场景 | 使用检索并复制一个 citation | 引用真正支持结论、无证据时会拒绝编造 |
| direct 场景 | 没调用工具 | 回答确实为 4（现脚本未断言） |
| `scripts/legacy_smoke_two_turn_path.py` | 曾有两轮目录回归脚本 | 当前精确 checkpoint 恢复；脚本未显式传前轮 checkpoint，需要更新 |
| evaluation/results/*.json | 历史实验材料 | 当前 PydanticAI 基线：抽查 csv-1 为已淘汰 OpenHands 内核 |

另外，当前检查型请求的 complete-report tool lock 会收起后续工具；这必须计入系统配置，并用“同一请求检查两个目录、还需知识核验”的挑战案例检查过早停止。工具已返回数据不代表用户目标全部完成。

旧记录保留，标为 legacy/smoke；缺少契约、配置、重复数或独立验证的记录不回填正式分数。85 项工程测试通过不能换算成 Agent 85 分。

## 3. 三条测试轨道，分别出分

| 轨道 | 入口与证据 | 主要用途 |
|---|---|---|
| agent | 真实 Qwen → 已部署 API → Action/Job/Artifact → 独立验证 | 通用任务、林业结果、知识与上下文能力 |
| engineering | pytest/可控故障注入 → SQLite/容器/文件实态 | 幂等、权限、恢复、取消等发布门禁；允许 mock，但必须注明 |
| ui | 真实浏览器 → 请求 → DOM/截图/性能时间戳 | 消息可见、会话稳定、刷新恢复；真实模型不是渲染测试的必要条件 |

禁止混合三条轨道计算平均分。UI 用受控服务器可以隔离前端缺陷；正式端到端案例另绑定真实 Runtime。HTTP 测试不能冒充 UI。单个工具的确定性数值测试不能冒充 agent 任务。

首轮 agent 三个能力组：通用执行、林业 UAV、知识/上下文。每组 4 个基础任务，共 12 个，每任务重复 3 次；另有 4 个 engineering 门禁与 2 个 UI 用例。机器契约见 suite.json。36 次模型运行只是研发试点，不能解释为高可靠认证。

## 4. 每个任务怎样判

执行前冻结：自然语言目标、输入版本、允许读写范围、可选工具/库、预期交付物、必需检查、容差、时限、资源预算、故障注入时间点、适用配置、重复次数。gold、断言与 verifier 存在 Agent Workspace/知识库之外。

每个必需检查只能是 pass / fail / unknown，必须指向独立 verifier 报告及原始证据（事件序号、数据库行、产物位置、页面观测）。计分器要求证据文件存在，但文件存在不证明内容真实；采集器和 verifier 属于受信评价端，需要代码审查及反例测试。模型自己输出 passed=true 无效。

任务严格成功需要：运行达到契约预期终态、所有必需检查通过。预期“拒绝越权/报告数据不足/安全暂停”的任务也可以成功；不能统一要求 Runtime completed。退出码 0、调用成功、文件存在、回复非空均不足以单独判成功。

| 对象 | 独立判据与反例 |
|---|---|
| CSV/JSON | 按业务键核对全量小型 fixture 的记录、类型、空值和数值；行列顺序只在需求规定时重要。不能只验行数或相关系数 |
| 栅格 | CRS 的语义等价、仿射网格、范围、波段角色、单位、有效掩膜、解析可计算像元。不能把高相关误当无偏：整体乘 10 仍可相关为 1 |
| CHM | 独立 DSM−DTM 真值、共同有效像元、垂直基准/单位、负值事实、源数据不变；地理坐标或未知基准应报告条件不足 |
| UAV 清单 | 人工冻结的小型清单 + 样本 EXIF；核对主航线/参考板/历史成果和统计范围。1605白桦单独作为真实回归，不作为泛化盲测 |
| 单木候选 | 合成 fixture 验证数学行为；真实数据需要独立样地/人工标注。没有真值时只评产物与表述，不报真实总株数精度 |
| RAG | gold 支持段落与版本；检索 Recall@k、引用可解析率、逐声明支持率、无答案时正确拒答分开；命中 citation 不等于支持结论 |
| UI | 浏览器点击时间、首次用户气泡 paint、选中会话、事件去重与终态；两次 POST 很快不能证明气泡及时出现 |

对标量，先核对单位/定义，再用 |预测−真值| ≤ max(abs_tol, rel_tol×|真值|)。零附近使用预先规定的绝对容差，不用相对误差除以零。缺失、NaN、无穷不是零误差。容差来源必须是解析精度/仪器规格/独立领域认可，不按本次模型结果放宽。连续误差只供诊断，不挽救关键断言失败。

开放文字采用冻结的事实单元评分表：准确陈述、必需覆盖、证据支持、反向/过度结论分别检查。优先机器核对结构化交付，语义由盲审复核；judge 模型只能提取候选声明或辅助标注，不给主观 1–10 总分。双人标注试点报告一致性及分歧仲裁；没有复核标为 unknown。自然语言改写不因没命中关键词就扣分。

## 5. 得分的确切含义

设任务 i 预先安排 n_i 次运行（本版 agent 为 3）；第 j 次完整成功 X_ij=1，已验证失败 X_ij=0。p_i=ΣX_ij/n_i。能力组 g 的分数为 S_g=100×mean_i(p_i)；agent 概览为三个组的等权均值，并始终同时显示组分和最差组分。

这里等权是公开的研发覆盖选择，不是自然定律。不能靠增加同一类简单样本改变权重：同一个基础任务的改写/扰动属于同一任务簇，先簇内平均，再组内平均。后续真实使用日志稳定后再增加场景权重列，不替换主报告。每个分数表示冻结任务分布上的完整成功比例，不代表“智力”“自主性”或所有林业任务的成功概率。

缺少检查、缺少证据、未运行、环境故障都保留为 unknown，不从预定分母删掉。不完整时不发布正式组分；报告“已证明成功的下界～把未知全部当成功的上界”和完成覆盖率。上下界是缺失证据边界，不是置信区间。已知超时/超资源/系统崩溃属于失败；verifier 本身损坏属于 unknown，修复后全组复算。环境故障须有预检/探针证据；另报端到端可用率，不把模型故障改标环境故障。

门禁独立显示 pass/fail/unknown；任意失败阻止发布，未知代表验收未齐，不能“默认通过”。门禁包括源只读与权限、离线/联网安装隔离、输入/副作用不重复、安全恢复与取消。拒绝合法请求不会触犯门禁，但相应任务失败，防止“什么都不做最安全”。普通科学误差导致任务失败；仅事前指定的关键断言才升级为门禁。

当前不设 80 分发布线。报告只给 blocked / incomplete / measured_unqualified：分别表示发现门禁失败、证据未齐、完成测量但尚无批准且经过校准的发布政策。后续用真实任务失败成本确定每组最低率、关键错误上限与延迟 SLO，提前冻结，再在盲测集检验。

## 6. 重复、统计与公平比较

- 每次干净会话/Workspace；只在多轮任务内部继承检查点；项目记忆只按案例契约初始化。知识源快照相同，不把 gold 放入 RAG。
- 模型固定 qwen3.8:27b 的实际 digest，thinking=true、temperature=0.2、context=32768、output=8192；记录 Ollama、依赖、容器 digest、工具开关、Prompt、源码含脏改动的快照、GPU/内存、冷/热启动、预算和 evaluator 版本。只保存小型配置/代码快照；不为本次评测哈希整批大型遥感数据。
- 三次全部计入；不挑最好一次，不把 best-of-3 叫成功率；修复后重跑叫新版本。记录每题三次全成功比例 all3 和各次结果。相同 seed 也不保证推理确定，记录供应端是否真正接受 seed。
- pilot 每组只有 4 个基础任务，先公布逐题结果和 min/max，不伪造精确总体 CI。扩展到有代表性的独立任务簇后按任务簇分层 bootstrap；重复、近义改写、同一地块的文件不作为独立样本。不要把 3/3 成功说成 100% 可靠。
- A/B 固定同一数据、题目、资源和采样，交错运行；报告每题配对差、退步例和成本。CI 跨 0 表示未证实提升，不等于证明等价。以项目/地块/日期分割 dev 与 holdout；1605白桦及其改写仅 dev。测试集冻结后禁止用失败例反复调 Prompt 再宣称盲测。
- 能力允许工具或自主代码实现等价解。定向工具协议测试另标 instructed，不能计为 autonomous。固定预算下对比同模型 Harness；换模型另表。跨产品需要同输入/权限/库和执行环境，不能拿论文排行榜数直接比较。
- 消融一次只改一个条件：RAG 开关、记忆开关、插件开关或 report lock。RAG 测“有益检索/不需检索/查无依据”；记忆测提升与负迁移；插件关闭测通用任务不退化。

## 7. 诊断指标与优先级

不评分私有思维链、文字长度、反思次数、计划格式和专家轨迹 embedding 相似度。规划用可观察效果诊断：是否满足依赖条件、错误后改变有效条件、完成必要任务后停止。工具协议错误率分参数校验/业务失败/注入故障；正确诊断后的恢复性重试不能算盲重试。

每次运行分开测：点击→用户气泡、POST ACK、首个 thinking/正文、首个有效工具结果、最终交付；记录 p50/p95 的样本数。样本少时列原始值与最大值。估算 token 与供应端 usage 分开；无供应端账单时成本为 null。按成功任务看效率，同时保留失败及超时的成本，不能靠少做任务换高效。

失败标签：ui_state / input_checkpoint / duplicate_side_effect / permission / tool_protocol / path_grounding / data_semantics / algorithm_numeric / retrieval / unsupported_claim / context_loss / premature_stop / resource / infrastructure / verifier。允许多个标签；根因未知就记 unknown，不能凭最后一条报错武断归因。

修复顺序由报告驱动：门禁失败 → 用户消息/恢复等阻断 → 最差能力组的高频失败 → 已正确任务的延迟/成本。每个改动先绑定失败 case，再用同一配置做配对回归。首批优先 UI 实际点击、CSV+脚本修复、多目录只读检查、引用是否支持结论；然后扩充独立地块和多光谱数据变体。

## 8. 最小工程落地与当前边界

复用 RunStore 事件、Step Context 清单、Action/Attempt/Job/Artifact、SDK checkpoint，评价器离线读取；不添加 Agent 内核、模型循环或生产管理后台。

已落地：本协议、suite.json 的 18 个任务契约、scorecard.py 的确定性聚合/容差比较、计分器反例测试。计分器拒绝错误轨道、配置混杂、重复运行槽位、额外次数以及无证据 pass；未提供记录时报告 incomplete。它不自动验证语义/视觉，也不把旧烟测结果导入新分数。

当前 verifier 覆盖（2026 年本轮）：agent 轨道 8/12 个 case 的 24 项检查已实现并各自有反例测试——core.paths、core.csv、core.repair、core.changed_input、forestry.inventory、forestry.product_qa、forestry.chm、forestry.ndvi；engineering 与 ui 轨道的 6 个 case 共 8 项检查此前已实现。合计 32/43 项检查。`tests/test_evaluation_pipeline.py` 会逐 case 断言「声明 = suite 检查 = 可导入的 verifier」，因此新增 case 若检查名无人实现会立即失败，而不再表现为整题 unknown。

尚未实现的是 knowledge_context 组的 4 个 case 共 11 项检查。它们不是普通的单轮采集，需要先补三样基础设施：

1. **项目与知识源播种**：`POST /projects`、`POST /projects/{id}/knowledge/sources`（202 异步索引）、`PUT /sessions/{chat_id}/project` 已经存在，但 collector 只做「上传附件 + 一次 POST /runs」。需要一段可复用的播种步骤，并且轮询索引完成后再提问。
2. **多轮采集驱动**：knowledge.memory 要求在保存/更新/删除记忆后继续同一 Run（`POST /runs/{run_id}/messages`），knowledge.context 要求长历史触发真实压缩后继续未完成目标。现有 `collect_trial` 只发一条消息，`evaluation/collect/` 需要增加多轮版本。
3. **压缩证据**：compact `Step/checkpoint` 证明实际触发压缩。`normalize_trace` 已记录 `checkpoint_state`，但需要确认事件流里有可判定的压缩标记；没有就只能记 unknown，不能凭回答长度推断。

在这些就绪之前，`python evaluation/scorecard.py` 会把 knowledge_context 组报为 incomplete 并保留在分母里，这是预期行为，不是回归。

接入顺序：①按 case 冻结 fixture/gold 与独立 verifier；②真实部署 API 采集全量事件和选定产物；③真实浏览器采集 UI；④运行 12×3 次 Qwen pilot，输出第一版分组基线；⑤根据失败分布补 holdout 并做 A/B。suite 中的 acceptance 是待实现/复核的具体判据，不表示全部已自动运行。

离线查看当前覆盖：`python evaluation/scorecard.py`。使用证据包：`python evaluation/scorecard.py --records evaluation/work/baseline/records.json`。标准输出为 JSON，可由调用方保存。缺少记录返回退出码 2；门禁失败 1；完整测量返回 0（仅表示测量完成，不代表发布合格）。
